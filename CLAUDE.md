# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Portuguese property-management SaaS (Lovable.dev project, ID `41f0b728-9844-4411-ac68-b65a5c54f948`). Domain language is Portuguese — keep entity names in Portuguese:

- **condomínios** — buildings managed by the property manager
- **ativos** — building assets (extinguishers, SADI/SADC, gas, solar, insurance, elevator licenses…)
- **ocorrências** — issues/incidents reported against a building
- **trabalhos** — maintenance jobs
- **técnicos** — technicians who apply to / are assigned to jobs

Cross-feature link: an *ocorrência* can spawn a *trabalho*; a *trabalho* references a *condomínio* + *técnico*; *ativos* belong to *condomínios*. See `claude-code-prompt.md` for the original feature spec (DB schema, status flows, matching logic).

## Commands

```sh
npm run dev         # vite dev server on port 8080 (host "::")
npm run build       # production build
npm run build:dev   # development-mode build
npm run lint        # eslint . (flat config in eslint.config.js)
npm run preview     # preview production build
```

No test runner is configured. Both `package-lock.json` and `bun.lockb` are present — npm is the documented installer (per README); pick one and stick with it for a given change.

Supabase migrations live in `supabase/migrations/` (timestamp-prefixed `.sql`). Apply via Supabase CLI or SQL editor against the project — there is no automated migration runner wired into the build.

## Architecture

### Stack
Vite + React 18 + TypeScript, shadcn-ui (Radix primitives in `src/components/ui/`), Tailwind, React Router v6, TanStack Query (provider mounted but most data flows through Context, not query keys), Supabase JS for auth/DB/storage, Leaflet for maps, jsPDF for document generation, xlsx for import/export.

Path alias: `@/*` → `src/*` (configured in both `vite.config.ts` and `tsconfig.json`).

### Routing & layout (`src/App.tsx`)
- Public routes: `/`, `/login`, `/signup`, `/onboarding`, `/t/:token` (public technician view of a job).
- Authenticated routes are wrapped by `<ProtectedRoute>` → a stack of feature Context providers (`Condominios → Ativos → Ocorrencias → Trabalhos → Tecnicos`) → `<AppLayout>` (sidebar + `<Outlet/>`).
- Adding a new feature with shared state usually means adding another provider in this stack.

### Data layer pattern
Every feature follows the same three-layer shape — **prefer extending these existing layers over inventing new ones**:

1. **`src/api/<feature>.ts`** — thin module exporting `<feature>Api` with `getAll/create/update/delete` etc., calling `supabase` directly. Defines and exports the row TypeScript interfaces.
2. **`src/context/<Feature>Context.tsx`** — provider that owns the in-memory list, loading state, search/filter UI state, and wraps each api call with toast feedback. Exposes a `use<Feature>()` hook.
3. **`src/pages/<Feature>Page.tsx`** + **`src/components/<Feature>Form/`** — UI consuming the context.

### Supabase client — IMPORTANT
There are **two** Supabase client modules and they are *not* equivalent:

- `src/supabase-client.ts` — hardcoded URL + anon key. **This is the one the app actually imports** (every `@/supabase-client` import in `src/api/*` and `src/context/*` resolves here).
- `src/integrations/supabase/client.ts` — auto-generated by Lovable, reads `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` and is typed against `src/integrations/supabase/types.ts`. Currently unused by app code.

When adding new API modules, follow the existing convention and import from `@/supabase-client` unless you are deliberately migrating the app to the env-var/typed client (in which case migrate everything, don’t straddle).

### Auth
`AuthContext` (`src/context/AuthContext.tsx`) wraps `supabase.auth` and additionally maintains a `profile` row from a custom `users` table (PK `id_user` = auth user id, with `primeiro_nome`, `ultimo_nome`, `empresa`). Signup creates both the auth user and the profile row; login refuses unconfirmed emails. Anything user-scoped (e.g. `condominios.id_user`) should be set from `supabase.auth.getUser()` inside the api layer, as in `condominiosApi.create`.

### UI conventions
- shadcn-ui components live in `src/components/ui/` (do not edit ad-hoc; regenerate via shadcn if needed). `components.json` is configured with `style: default`, `baseColor: slate`, alias `@/components/ui`.
- Toast feedback: use `useToast()` from `@/hooks/use-toast` (ShadCN toast). `Sonner` is also mounted globally.
- All user-facing strings are Portuguese. Keep that convention.
- `LanguageContext` exists for i18n scaffolding — check it before hardcoding strings.

### Lovable integration
`vite.config.ts` enables `componentTagger()` from `lovable-tagger` in development mode only — this annotates components for the Lovable web editor. Do not remove. Pushed git changes round-trip back into Lovable.
